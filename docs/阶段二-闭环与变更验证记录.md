## 三、闭环实测一：粘贴正文 → 候选 → 证据 → 人工确认 → 发布 → 学生待办

通过 8099 实际 API 执行（维护者 `reviewer` / 学生 `student`，密码均为 `lingxun-demo`）：

1. 维护者登录，取得 CSRF。
2. `POST /api/maintenance/drafts`，`extractionMode=HYBRID`，正文含适用对象、报名时间、材料。
3. 实际返回：`mode=RULE_FALLBACK`、`status=DISABLED`，警告“LLM DISABLED，已回退规则模式”。
4. 三个字段的实际结果：

| 字段 | 状态 | 来源 | 证据判断 | 值 |
| --- | --- | --- | --- | --- |
| 学生/竞赛报名/适用对象 | CANDIDATE | RULE | SUFFICIENT | 全日制在校本科生 |
| 学生/竞赛报名/截止 | CANDIDATE | RULE | SUFFICIENT | 2026-11-10T17:30 |
| 学生/竞赛报名/材料 | CANDIDATE | RULE | SUFFICIENT | 报名表、学生证复印件 |

5. 逐字段 `PUT /api/maintenance/versions/{id}/fields` 确认，`POST /publish` 返回 `PUBLISHED`。
6. 学生登录并 `POST /api/matters/{id}/subscription`，`GET /api/todos` 实际返回：

```text
TODO_ID=2 STATE=PENDING DUE=2026-11-10T17:30 TITLE=闭环验证-混合回退
```

结论：粘贴文本 → 规则回退抽取 → 字段级证据 → 人工确认 → 发布 → 学生待办，在真实后端接口上闭环成功。该次 HYBRID 实际是规则回退，不能称为“LLM 混合闭环”。

## 四、闭环实测二：新旧通知变更 → 待办复核 → 学生确认

在同一事项上建立 V1 与新版本：

- V1 截止：`2026-11-20T17:00`；发布后学生待办 `PENDING`，`dueAt=2026-11-20T17:00`。
- 新版本 V2 截止：`2026-12-04T17:00`；人工确认后发布。
- `GET /api/maintenance/versions/{id}/change-impact` 实际返回：

```text
IMPACT_ROLES=学生
FIELDS=1
TASKS=1
TREATMENT=覆盖
OLD=2026-11-20T17:00
NEW=2026-12-04T17:00
```

- 发布后学生待办实际变为 `REVIEW`，`dueAt` 为空；日历实际不含旧日期 `20261120`，也不含新日期 `20261204`。
- 学生 `PATCH /api/todos/{id}` 确认新版本后：

```text
TODO_AFTER_CONFIRM=PENDING
DUE=2026-12-04T17:00
日历：旧日期 False，新日期 True
```

结论：过期/有争议的截止日期没有继续作为有效日期；变更影响角色和学生截止待办被实际标出；学生确认后才启用新日期。此链路有后端集成测试和 8099 实际 API 双重验证。

## 九、下一阶段建议（按优先级）

1. **真实 LLM 验签**：用户在本机设置环境变量后重启，执行一次 HYBRID 抽取，核对 `version.extraction.status` 与抽取字段，保存真实调用证据；不把 Key 写入仓库或聊天。

3. **变更漏检/误报评测**：把同一事项真实改期对纳入数据集，计算 `ChangeAnalyzer` 的漏检率和误报率，再决定是否扩展规则。
4. **Flyway 迁移**：给 `notice_version` 增量列、`version_extraction` 建迁移脚本和回滚策略。
5. **前端 E2E**：覆盖维护端录入→核验→发布，学生端订阅→待办→确认，浏览器自动断言。
6. **OCR/PDF 扫描件**：在明确本地低成本前提下评估 Tesseract 或调用外部 OCR，不默认开启。
7. **Git 提交与推送**：在先核对 diff、无 Key/无临时文件后，提交并推送。
