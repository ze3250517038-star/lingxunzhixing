## 0. 审计结论摘要

1. **现有系统不是空壳演示**。学生端与维护端均为真实 Vue 3 SPA，所有核心页面调用 Spring Boot `/api`；登录、角色、CSRF、通知快照、字段候选、证据区间、人工核验、发布事务、待办、办理清单、ICS 日历和审核记录均有真实后端实现。
2. **现有能力足以作为挑战杯原型的可靠基线，但距离“科技发明制作 B 类”的技术真实性仍有明显差距**。当前的核心能力是“固定规则抽取 + 人工核验 + 版本快照 + 待办”，不是完整意义上的智能语义理解，也没有可复现的科研评测。
3. **本轮回归测试真实通过**：后端 `NoticeDatesTest 25 项 + NoticeWorkflowTest 11 项 = 36 项，Failures 0 / Errors 0 / Skipped 0`；前端 `vite build` 成功，31 个模块，产物与审计前一致。测试报告时间戳为 2026-11-23 00:23。
4. **本轮发现了必须优先修复的技术风险**，其中最重要的三项是：
   - `TodoView.dueAt` 在 `REVIEW` 状态下仍可能返回旧截止日期，虽然 ICS 导出已阻断，但 API 消费方仍可能把旧日期当作有效日期（`NoticeWorkflow.java:558-566`）。
   - 证据只校验“原文中确实存在这段字符”，没有校验“这段原文是否足以支持该字段结论”；人工修正可以把无关片段绑定为证据（`NoticeWorkflow.java:479-496`、`:247-264`）。
   - 当前没有任何 LLM、网页正文抓取、PDF/Word 解析、学生资料匹配或科研评测工具；这些是挑战杯升级的核心缺口，不是 UI 功能缺口。
5. **建议不推倒重做**。保留 Vue 3、Spring Boot、Java 17、`JdbcTemplate`、`notice_version.fields_json` 和现有接口，以“增量的来源层、抽取层、证据层、变更层、匹配层、评测层”改造；现有 36 项测试作为回归基线。
6. **本轮未修改任何 `src` 业务源码**。新增了本审计报告和两个只读审计脚本；重新构建了 `frontend/dist` 与测试报告。`mvn package` 因 8096 旧进程占用 `backend/target/lingxun-0.1.0.jar` 而在 repackage 阶段失败，这是环境锁文件问题，不是编译失败；`mvn test` 已完成编译并通过。

## 2. 当前系统架构与真实数据流

```text
Vue 3 SPA (App.vue / NoticeDiff.vue)
        │  fetch /api，X-Lingxun-Token 自定义 CSRF 头
        ▼
PortalController（统一 REST 入口，角色和 CSRF 校验）
        ▼
SessionAccess（BCrypt、session fixation 防护、角色、CSRF）
        │
        ▼
NoticeWorkflow（事务、规则抽取、证据校验、版本发布、待办同步）
        ├── NoticeRules（固定标签正则 + 固定 Slot）
        ├── NoticeDates（中文日期归一化）
        └── TodoCalendar（iCal4j 导出）
        ▼
JdbcTemplate → H2（demo，内存）/ MySQL（默认 profile）
```

- 后端是单体分层，不是微服务；这一结构对本项目是合理的低成本选择，升级时不应为了“看起来先进”拆成多个服务。
- `notice_version` 以 `snapshot` 保存通知全文，以 `snapshot_hash` 防重，以 `fields_json` 保存字段/候选/证据；`todo` 保存订阅生成的任务，`todo_step` 保存清单勾选，`audit_event` 保存操作文字记录。
- 前端是单文件主界面（`App.vue` 约 1,389 行），通过 `page` 状态切换学生端 7 个页面和维护端 4 个页面；不是静态 HTML 演示。

## 4. 关键技术维度审计

### 4.1 安全性

**已做对的：**

- `SessionAccess.login():54-65` 使用 BCrypt，密码字节长度限制 72，登录后 `request.changeSessionId()`，CSRF token 使用 `MessageDigest.isEqual` 常量时间比较。
- 所有 mutation 都有 `X-Lingxun-Token` 校验（`:73-75`）；角色检查在 Controller 统一执行。
- SQL 全部使用 `?` 占位符，未发现字符串拼接用户输入；唯一动态 SQL 是 `FOR UPDATE` 常量和仅由内部布尔值决定的 `lock ? " FOR UPDATE" : ""`，不构成注入。
- 前端未使用 `v-html`/`innerHTML`；通知原文、反馈、审核详情均通过 Vue 插值转义。
- `officialSource():679-693` 限 HTTPS、无 userInfo、端口 443、host 为 `sgu.edu.cn` 或子域。
- 异常处理不回传堆栈（`ApiExceptionHandler.java:61-66`）。

**仍需补的：**

| 风险 | 证据 | 影响 | 建议 |
|---|---|---|---|
| 登录无失败限流/锁定 | `SessionAccess.login()` 没有尝试计数 | 可被暴力尝试 | 按 IP/账号滑动窗口限流，失败日志脱敏；锁定策略可配置 |
| 安全响应头缺失 | live HEAD：CSP 等 6 项 MISSING | XSS/点击劫持/信息泄漏防护不足 | 加统一 Filter，至少 CSP、X-Content-Type-Options、X-Frame-Options、Referrer-Policy；HTTPS 环境加 HSTS |
| Cookie Secure 默认 false | `application-mysql.yml:14-16`，live demo 无 Secure | HTTPS 生产若忘配会降级 | 生产 profile 强制 true 或启动校验 |
| 无文件上传/网页抓取安全策略 | 功能尚未实现 | 未来 SSRF、恶意文件、压缩炸弹 | URL 抓取限域+手动重定向+大小/超时；上传限 MIME/大小/页数；禁止外链资源 |
| CSRF token 可从 `/api/session` 读取 | `SessionAccess.inspect()` 返回 csrf | XSS 可绕过 CSRF | CSP + 输出编码 + 不把 token 暴露给第三方脚本；保持 SameSite |
| 审核日志无分页/过滤/敏感信息遮蔽 | `events():470-477` 固定 `LIMIT 100` | 生产审计可用性不足 | 按事项/版本/actor/action 过滤；敏感字段脱敏；保留期限策略 |
| 生产账号空密码不报警 | `provision():39-46` 空密码直接 return | 部署后无人可登录，或误以 demo 账号上线 | 启动校验：非 demo 且无账号/密码时 fail-fast，不静默启动 |

**本轮 live 安全验证结果（真实）：** 未登录 `/api/todos` 401；学生 `POST /api/maintenance/versions/1/publish` 403；维护者无 CSRF 发布 403；学生 `GET /api/maintenance/audit` 403；维护者 200。说明现有核心权限不是前端假拦截。

### 4.2 数据一致性、事务与幂等

**已做对的：**

- `draft/candidates/review/correct/publish/withdraw/subscribe/unsubscribe/updateTodo/updateStep/feedback/handleFeedback` 均有 `@Transactional`（`NoticeWorkflow.java` 多处）。
- `publish()` 先锁 matter，再重新读 draft，比较 `baseVersionId` 与 `currentVersionId`；并发发布测试真实得到 200/409。
- `notice_version` 有 `(matter_id, version_no)` 和 `(matter_id, snapshot_hash)` 唯一约束（`schema.sql:14-29`）。
- `updateTodo` 使用状态 CAS：`WHERE id=? AND username=? AND todo_state=?`（`:397-399`），状态变化后拒绝。
- 重复发布当前版本会在 `:278` 直接返回，重复处理同一反馈使用 `handled=FALSE` 条件更新（`:465`）。

**仍需处理的竞态/幂等点：**

| 点 | 证据 | 风险 | 建议 |
|---|---|---|---|
| 并发订阅 | `subscribe():311-318` 先 `subscribed()` 再 INSERT | 两个并发请求可能撞唯一键 | `INSERT ... ON DUPLICATE` 或捕获唯一键并返回成功；加并发测试 |
| 发布时补 todo | `addMissingTodos():548-556` 先查 existing 再逐条 INSERT | 并发发布/订阅下可能重复插入 | 唯一键 + 幂等 upsert；在同一 matter 锁内完成 |
| 清单勾选 | `updateStep():418-425` 先 UPDATE，changed=0 再 INSERT | 并发勾选可能重复插入/丢失更新 | `MERGE`/`INSERT ... ON DUPLICATE KEY UPDATE`；加版本条件 |
| `fields_json` 无校验和 | `saveField()` 直接覆盖 LONGTEXT | 手工/异常写入可能产生不可解析 JSON | 增加 `fields_hash` 或读取时校验；发布时强校验 |
| 审计不覆盖所有写操作 | 例如 step 勾选、普通 DONE 变更没有 audit | 用户操作不可追溯 | 关键写操作统一审计，记录 before/after、actor、版本 |
| `TodoView.dueAt` 的旧值 | `:563-566`：`dueAt=previous` 后即使 current 未确认也不清空 | 旧截止日期可能被外部消费 | 在 REVIEW/HOLD 时把 `effectiveDueAt` 设为 null，单独保留 `previousDueAt`；ICS 继续排除 |

### 4.3 日期处理

- `NoticeDates` 支持中文年月日、同月简写区间、跨年、相对年份、时间、多处日期、区间倒挂、非法日期；`NoticeDatesTest` 25 项真实通过。
- 服务端 ICS 固定校园时区 `Asia/Shanghai`（`TodoCalendar.java:24`），全天事件结束日 +1，符合 iCalendar 的 exclusive end。
- 发布和人工修正都拦截“截止日期早于通知日期”（`correctField():206-214`、`verifyDeadlines():498-513`）。

**风险：**

1. 前端 `dateKeyDays()` 和 `dueDays()` 使用浏览器本地 `new Date()`（`App.vue:227-247`），不是校园时区。学生在境外/时区设置错误时，“今天”“逾期天数”“未来 14 天”可能偏一天。应改为服务端返回 `today`/`timeZone`，或前端固定用 `Intl.DateTimeFormat(..., {timeZone:'Asia/Shanghai'})`。
2. 当前 `todoDueKey()` 只取 `dueAt` 前 10 位，带时间的截止在“剩余天数”计算中丢掉时间；日历导出仍按完整时间。展示口径需要统一。
3. 日期处理强依赖原文字符串和 `noticeDate`；没有“发布日/生效日/办理阶段起止”的独立字段。对“补发通知”“更正通知”场景，`noticeDate` 是否是生效日需要产品定义，不能默认。

### 4.4 证据定位与充分性

**已实现：**

- 每个候选 `Choice` 带 `Evidence(versionId, fragmentNo, global start, global end, quote)`（`Models.java:13`、`NoticeRules.java:65`）。
- `verifyChoice()` 重新读取证据所属版本，检查 matter 一致、片段号合法、区间落在片段内、`snapshot.substring(start,end)==quote`（`:479-496`）。
- 人工修正 `correctionEvidence()` 同样要求片段号、字符区间、非空白，且拒绝“暂定/待定”（`:247-264`）。
- live V1 的 6 个字段全部切片一致，说明现有证据链不是静态伪造。

**关键缺口：**

1. **没有“证据是否支持结论”的校验。** `verifyChoice()` 只证明 quote 存在；`correctionEvidence()` 不检查 quote 是否包含字段值、日期或角色词。一个审核者可以把“材料要求：身份证”选作“截止日期”的证据，仍可能通过。
2. **没有证据来源类型/定位器。** 未来从网页、PDF 导入时，仅有全局字符偏移不足以让评审者回到 PDF 页码/HTML 段落；需要 `sourceDocumentId + page/paragraph/selector + char offsets` 的联合定位。
3. **没有歧义/冲突的强制 HOLD 规则以外的“支持度”。** 当前 `HOLD` 是人工选择；没有 `SUFFICIENT/WEAK/IRRELEVANT` 自动判定，也没有“已确认但证据弱”的发布拦截。
4. **人工修正可覆盖错误但不可追踪“为什么认为足够”。** 目前有 reason 文本和 audit，但没有结构化 `supportLevel`/`supportReason`。

### 4.5 通知版本与变更语义

**已实现：**

- 同一 matter 的版本链：`baseVersionId`、`version_no`、`snapshot_hash`；`candidates()` 继承已确认字段，值不同标覆盖，多候选标冲突。
- 发布时检查所有字段不为 `CANDIDATE`，逐项复核证据，检查截止日期；在事务中切换 current_version，`synchronizeTodos()` 逐 todo 判断：
  - 字段缺失/`NOT_APPLICABLE` → `IGNORED`
  - 旧待办已 REVIEW 或字段/依据变化 → `REVIEW`
  - 未变化 → 更新 acknowledged
- `withdraw()` 全量转 REVIEW；`calendarDeadlines()` 只选 current=target=acknowledged 且 PENDING 的已确认学生截止。

**缺口：**

1. 没有独立的 **change report**（字段级 `INHERIT/OVERRIDE/CONFLICT/UNKNOWN` + 影响角色/阶段/待办统计）。当前只有字段上的 `change` 字符串和 todo 状态。
2. “语义变更”仍是值字符串比较；`requirements()` 比较字段 key/state/describe/quote，不是语义等价。比如原文改写但值相同，可能被标“覆盖”；反过来，条件措辞变化但实质相同也可能被误报。
3. **旧日期暴露风险**：`TodoView.dueAt` 在 REVIEW 时取 previous 的值，API 消费方可能误用；前端文字虽然写“旧日期已停用”，但这只是 UI 约束，不是数据契约。
4. 变更影响只到单条 todo，没有“该变更影响哪些 role/stage、多少学生、哪些任务需要复核”的聚合报告，不利于挑战杯演示“影响传播”。
5. `synchronizeTodos()` 的 `affected` 公式在字段未确认时直接受影响，方向正确；但没有把“仅材料变更”与“截止变更”分级，也没有通知学生具体变更字段。

### 4.6 个性化待办

当前是“订阅 + 固定学生截止字段”：
- `Models.Field.actionable():29-32` 只把 `role=学生`、`type=截止`、`stage in [学分申报,竞赛报名]` 的字段转成 todo。
- `subscribe()` 只写 subscription 并补 todo；`todoSteps()` 的“确认自己是否符合条件”是让学生手工勾选，不是系统判断。
- 没有 `student_profile`，没有学院/年级/专业/学位类型/就读方式，也没有从通知的“适用对象”提取结构化条件。
- 因此，系统能告诉学生“有一个截止”，但不能判断“这个学生是否适用”，更不能在通知条件变化后重新匹配所有学生。

## 6. 最小改造方案（保留现有架构，增量演进）

### 6.1 设计原则

1. **保留** Vue 3、Spring Boot 3.5.8、Java 17、`JdbcTemplate`、现有 REST 路径、`notice_version.fields_json`、现有 36 项测试。
2. **先证据，后智能**：任何 LLM 输出都必须回到原文定位；定位失败/歧义/无依据一律 HOLD，不允许自动确认。
3. **一处事实来源**：`snapshot` 是原文事实；`fields_json` 是当前字段事实；新增证据索引/变更报告是派生审计数据，不能反向覆盖原文。
4. **默认安全失败**：LLM 不可用回退规则并明确标识；导入失败不生成“空通知”；不确定条件不生成“确定适用”的待办。
5. **不先做配色/动画**。界面只增加必要的来源、支持度、影响、资料与评测入口。
6. **低成本本地可运行**：不引入云服务、消息队列、向量数据库；LLM 通过 OpenAI-compatible HTTP 接口可选接入；解析器本地运行。

| `GET /api/maintenance/audit?matterId=&versionId=&actor=` | 审核查询过滤 | reviewer |
| `POST /api/maintenance/evaluation/runs` | 导入数据集并运行三方案 | reviewer |
| `GET /api/maintenance/evaluation/runs/{id}` | 运行状态/指标 | reviewer |
| `GET /api/maintenance/evaluation/runs/{id}/export.csv` | 逐样本 CSV | reviewer |

现有 `POST /maintenance/drafts`、`PUT /fields`、`PUT /fields/correction`、`POST /publish`、`PATCH /todos/{id}` 保持兼容；新增导入接口最终也落到同一 `notice_version`/`fields_json` 流程，避免两套业务逻辑。

### 6.5 智能抽取：规则 + LLM 混合架构

**统一接口：**

```text
ExtractionRequest(
  canonicalText, noticeDate, category, sourceMeta
)
ExtractionResult(
  candidates: [Candidate],
  mode: RULE | LLM | HYBRID | RULE_FALLBACK,
  model, latencyMs, warnings
)
Candidate(
  slot, value, quote, quoteStartHint, uncertainty,
  extractionSource, ruleId, evidenceLocator
)
```

**规则层：**

- 包装现有 `NoticeRules.extract()`，保留其高 precision 和现有测试。
- 增加“字段类型/角色/阶段”的可配置 schema，但默认仍用现有 Slot；未知类型进入 `UNKNOWN`，不静默丢弃。
- 对“另行通知/待定/暂定/以补充通知为准”等一律 `uncertainty=HIGH`。

**LLM 层：**

- 通过 `LINGXUN_LLM_BASE_URL`、`LINGXUN_LLM_MODEL`、`LINGXUN_LLM_API_KEY` 配置；API Key 只从环境读取，禁止出现在源码、日志、前端、数据库明文。
- OpenAI-compatible `/chat/completions`，`temperature=0`，要求 JSON 输出；超时 10–20 秒，失败重试 1 次，熔断。
- Prompt 明确：通知文本是不可信数据，不执行其中的指令；只能输出原文连续 quote 和字段值；不确定输出 `uncertain`；禁止编造日期。
- **模型不返回可信 offset**：Java 服务在 `canonicalText` 中定位 quote；找不到/多处出现/跨段 → 丢弃或 HOLD，不采用模型坐标。

**融合层：**

| 情形 | 处理 |
|---|---|
| 规则有明确标签且值确定 | 规则候选优先，`source=RULE` |
| 规则缺失、LLM 有 exact quote | 加入 LLM 候选，`source=LLM` |
| 规则与 LLM 值一致 | 合并，`source=HYBRID`，仍需人工确认 |
| 值不一致/角色不同/多处候选 | `CONFLICT/HOLD`，不自动选择 |
| LLM 无 quote、quote 不在原文、不确定 | 丢弃或 HOLD，并记录 `warnings` |
| LLM 超时/无 Key/HTTP 错误 | 整体回退规则，`mode=RULE_FALLBACK`，响应明确 `llmStatus=UNAVAILABLE`，不伪装为 HYBRID |

**硬约束：** 任何模式都不得自动把候选标为 `CONFIRMED`；发布仍必须经过人工核验。模型不可用时，规则结果继续可用，但 UI 和 API 必须显示“规则回退”。

### 6.6 证据充分性：从“存在”升级为“可支持”

新增 `SupportAssessor`，对每个 `(field, quote)` 做保守判断：

| 字段类型 | 最低证据要求 | 不满足时 |
|---|---|---|
| `截止` | quote 含可解析日期/时间，且该日期与 value 一致 | `INSUFFICIENT` → HOLD |
| `时间` | quote 含日期/时间或明确阶段 | HOLD |
| `适用对象` | quote 含对象词（年级/学院/专业/学生类别等），不是空泛“相关学生” | WEAK/HOLD |
| `材料` | quote 含材料名称或“材料要求”语义 | WEAK/HOLD |
| `入口` | quote 含 URL/系统/地点/办理动作 | WEAK/HOLD |
| 角色/阶段 | quote 或相邻标题能支持 role/stage | UNKNOWN/HOLD |

- `supportLevel`：`SUFFICIENT / WEAK / IRRELEVANT / UNKNOWN`；`supportReason` 可展示。
- 发布门禁：`CONFIRMED` 但 `supportLevel != SUFFICIENT` → 拒绝发布，除非审核者显式选择 `MANUAL_OVERRIDE` 并填写理由；该覆盖仍保持 `MANUAL_OVERRIDE` 标记，不伪装为自动充分。
- 人工修正时，若 quote 不含日期/值，直接拒绝；若含但语义弱，允许“人工覆盖”，必须写 reason 并进 `review_action`。
- 证据定位器：文本为 `fragmentNo + start/end`；HTML 增加 `domPath/paragraph`；PDF 增加 `page + char start/end`；所有定位器都指向 `source_document`，且 quote 必须可由定位器回切验证。

### 6.7 变更语义与影响传播

新增 `ChangeAnalyzer.compare(from, to)`：

| 类型 | 判定 |
|---|---|
| `INHERIT` | 同 key、同 normalized value、双方证据均 SUFFICIENT、无冲突 |
| `OVERRIDE` | 同 key、双方已确认、normalized value 不同 |
| `CONFLICT` | 一方多候选/ambiguity，或旧值仍出现在新版本，或证据不足 |
| `UNKNOWN` | 新版本缺字段、字段未确认、无法定位 |
| `NEW` / `REMOVED` | 旧无新有 / 旧有新无（单独列出，不混入 UNKNOWN） |

输出：
- 字段级 `detail_json`（旧值/新值/旧证据/新证据/变更原因）。
- 角色/阶段影响：`impactRoles`、`impactStages`、`impactTodoCount`、`affectedUsernames`（仅维护端可见，注意隐私）。
- `requiresReview`：任何 CONFLICT/UNKNOWN 或截止变更必须 true。
- 发布前生成 `change_report`；发布后同步 todo：
  - 截止/条件变化影响对应 role/stage 的 todo → REVIEW；
  - 仅材料变化 → 对应阶段 REVIEW，但截止仍用当前确认值；
  - 未受影响 → 继承，更新 acknowledged；
  - 争议/未知截止 → 不产生有效截止，todo REVIEW 或 IGNORED（按语义）。
- **API 契约修复**：`TodoView` 增加 `effectiveDueAt`（仅当前已确认且有效的截止），`previousDueAt`（历史展示）；在 REVIEW 状态 `effectiveDueAt=null`；ICS 只读 effective。现有 `dueAt` 可在过渡期保留为 effective 的别名，避免旧前端立即断裂，但测试必须锁定“REVIEW 不返回有效日期”。
- 并发：matter 锁 + `change_report` 唯一 `(from,to)`；重复发布同一 current 幂等；并发订阅/步骤改为 upsert。

### 6.8 个性化待办与学生资料

- 新增 `student_profile` 与 `GET/PUT /api/student/profile`；字段最少：学院、年级、专业、学位类型（本科/专科/研究生）、就读方式（全日制/非全日制）、特殊身份（如应届/往届）。
- 从“适用对象”字段抽取结构化条件，**不能直接自动生效**：LLM/规则提出 `predicate_candidate`，审核者在维护端确认后写 `applicability_rule`。
- 谓词示例：
  - `grade in [2022, 2023, 2024]`
  - `college in ["信息工程学院"]`
  - `degree_type = 本科`
  - `student_status = 在校`
- `ApplicabilityService.evaluate(profile, rule)` 返回 `APPLICABLE / NOT_APPLICABLE / UNKNOWN` 与原因。
- 订阅时只生成 `APPLICABLE` 的任务；`UNKNOWN` 生成“补充资料/待确认”提示，不生成确定截止；`NOT_APPLICABLE` 不生成或标记 `IGNORED`。
- 学生更新资料后重算，使用幂等键避免重复 todo；历史 todo 不删除，保留证据和旧适用性。
- 这是“个性化”的真实实现，不是让学生手动勾选“我符合条件”。

### 6.9 科研评测工具

**数据集格式（CSV 或 JSONL）：**

```json
{
  "sample_id": "S001",
  "matter_title": "...",
  "notice_date": "2026-10-26",
  "text": "...",
  "source_type": "REAL_NOTICE",
  "gold_fields": [
    {"slot": "学生/竞赛报名/截止", "value": "2026-11-02", "evidence_quote": "报名时间...", "label": "PRESENT"}
  ],
  "gold_changes": [],
  "notes": ""
}
```

**运行模式：**

| 模式 | 说明 |
|---|---|
| `RULE_ONLY` | 现有规则，真实可运行 |
| `LLM_ONLY` | 需要 Key；无 Key 时标记 `NOT_RUN`，不得用 0 分代替 |
| `HYBRID` | 规则+LLM；LLM 不可用时标 `RULE_FALLBACK`，按回退策略单独统计 |
| `SIMULATED_FIXTURE` | 测试用固定桩，仅供指标算法验证，不与真实结果混表 |

**指标定义：**

- 字段准确率：按 `(slot, normalized_value)` 完全匹配的字段数 / gold 字段数。
- 字段 precision/recall/F1：以预测字段集合与 gold 字段集合计算；日期先归一化。
- 角色错配率：预测字段的 `role/stage` 与 gold 不一致数 / 预测字段数。
- 证据定位成功率：预测字段中 `quote` 能在原文唯一定位且 `start/end` 回切一致的比例。
- 无依据输出比例：预测字段中没有有效证据（缺失/无法定位/quote 为空）的比例。
- 变更漏检率：gold 变更字段中未被标为 OVERRIDE/CONFLICT/REVIEW 的比例。
- 变更误报率：gold 未变字段中被标为变更的比例。
- 所有分母、排除项、样本数写入 `metrics_json`；不把 skipped 样本混入分母。

**CSV 列（逐样本）：**

`run_id, sample_id, data_source, run_mode, model, field_key, gold_value, predicted_value, value_match, role_match, evidence_quote, evidence_loc_ok, support_level, error_category, notes`

**强区分真实/模拟：**

- `data_source=REAL_NOTICE` 只能来自真实通知；`SIMULATED` 必须显式标记。
- `run_mode=REAL_LLM` 只有实际调用配置模型才可写；测试桩为 `SIMULATED_FIXTURE`。
- 报告首页打印 `dataset_sha256`、样本数、模型、prompt 版本、运行时间、执行人；没有真实运行时，指标列写 `NOT_RUN`。

**当前状态：未运行。** 本报告不提供任何字段准确率、召回率、F1、漏检率数字；这些必须在数据集和实际模型调用完成后生成。

### 8.1 数据集

- **来源**：韶关学院官网公开通知为主，辅以其他高校公开通知；只收集公开、可引用的文本，做去标识化；模拟补充通知单独标记。
- **规模建议**：第一阶段 60–100 条通知，覆盖学分认定、竞赛报名、奖助、实习/毕业等；每条人工标注 5–8 个字段及证据 quote；另建 20–30 组“同事项前后版本”对用于变更评测。
- **划分**：开发 40%、验证 20%、测试 40%；同一事项的不同版本不能跨训练/测试泄漏；变更对单独划分。
- **标注**：两名标注者独立标注，分歧由第三人裁决；记录标注指南、版本、Kappa（实际计算后再报告，不预设）。
- **真值**：字段值归一化为 ISO 日期/标准角色/标准阶段；证据 quote 必须能在规范文本中唯一定位；不能定位的样本标 `NO_EVIDENCE`，不强行给真值。

### 8.2 对照与消融

- B0：规则引擎（现有 + 扩展标签）。
- B1：纯 LLM（同一 prompt、temperature=0）。
- B2：混合（规则优先 + LLM 补缺 + 冲突 HOLD）。
- 消融：去掉 LLM 证据定位、去掉支持度门禁、去掉变更分析，分别观察指标变化。
- 统计：点估计 + bootstrap 95% CI；样本量不足时只报告描述统计，不宣称显著优于。

### 8.3 结果记录与禁止事项

- 每次运行记录：数据集 SHA-256、样本数、模型名/版本、prompt 版本、温度、超时、运行时间、是否真实网络调用、操作者。
- **禁止**：把测试桩结果写成真实 LLM 结果；把 demo 预置样本写成真实抓取；把未运行的指标填 0；用单条样本宣称总体准确率；用人工挑选样本冒充全量测试集。

## 9. 风险、假设与待确认事项

| 风险/待确认 | 影响 | 处理建议 |
|---|---|---|
| 没有真实 LLM API Key/额度 | 纯 LLM/混合实验无法真实运行 | 先完成规则与混合回退；有 Key 后再跑 B1/B2，报告中标 NOT_RUN |
